# Giga Meter analytics: PostHog tracking plan

What Giga Meter reports to PostHog, why, and which dashboard uses it. The event
names live in code in [`src/app/analytics/analytics-events.ts`](../src/app/analytics/analytics-events.ts);
keep this page and that file in step.

The goal is one question per dashboard: **is every critical flow working, and
when it isn't, why?** Every failure event therefore carries the same fields, so
one table can list them all.

## Ground rules

- **Who is who: device and app instance**, the two levels of the backend's
  registration table (`dailycheckapp_school`, now the app instance table).

  | Level | What it is | In PostHog | In the database |
  |---|---|---|---|
  | **Device** (the base unit) | One physical PC | The *person*, identified by the device ID | `device_id` on each registration row, on `measurements` and on the daily ping summary |
  | **App instance** | The app under one Windows user, for one registration. Every registration, manual or automatic, is a new one; a logout and a new registration is a new one too | The `app_instance` *group* and the `app_instance_id` property on every event | One `dailycheckapp_school` row: `app_instance_id` (unique), `registration_source` (`manual` / `auto`), the three hardware IDs and the device ID; also on `measurements` and `connectivity_ping_checks` |

  A device can have several app instances (several Windows users, or logins
  after logouts). What matters most is that **every device is live with at
  least one app instance**; app instances explain why one isn't, and which
  install a measurement came from. Both are grouped by `school`
  (`giga_id_school`) and `country` (ISO 2).
  - The device ID is a hash (version 5 UUID) of the PC's firmware UUID,
    motherboard serial and disk serial when it is first seen. It is kept as
    long as most of its readable values still match (a new disk alone keeps
    it); when most of them change, the PC counts as a new device and gets the
    hash of its new values. Null values are left out of the comparison.
  - So the ID is not recomputed from the values each time: the app can't
    work it out itself and takes it from the backend.
  - `device_id_flags` on `server_device_registered` say what the matching
    saw: `<field>_changed` (a value differs from the matched device's),
    `<field>_shared` (a value repeated across PCs, left out of matching),
    `conflict`, `nothing_readable`, and `duplicate_values` (a new PC's values
    hash to an ID another PC already has, so it gets a random ID instead).
  - The backend returns `device_id` from the app instance's registration and
    from the status check the app runs at every start. The status check sends
    the app instance's ID, so the answer is that instance's own row's device
    ID: several PCs can share a firmware UUID, and the latest row for the
    hardware ID and school can be another PC's. Installations registered
    before 2.0.4 are identified once the backend has given their row a device
    ID (their first measurement on 2.0.4 does).
  - The existing-installation lookup (`checkExistingInstallation`) gives the
    app no device ID: the registration it finds can be another PC's. The app
    registers its own app instance next and takes the device ID from that.
  - The app instance ID is generated by the app (`appInstanceId` in local
    storage) when it first tries to register, and kept for retries. An install
    from before app instances makes one at its first start on 2.0.4 and
    attaches it to the registration it has (`app_instance_claimed`).
  - Until the app knows its device ID (not registered yet, or a registration
    saved without one), events are anonymous; PostHog merges them into the
    device once it is identified, so the onboarding funnel still reaches it.
  - Backend events use the same device ID and app instance: a stored
    measurement's is the one stored with it; a refused measurement's comes
    from its registration (by `app_instance_id`, else `BrowserID`).
- **Sent with every event:** `app_version`, `app_mode` (`prod` / `stg` / `dev`),
  `is_electron`, once read `build_commit` and `os_version`, and once
  registered `app_instance_id`.
- **Every failure event** carries `error_code` (a short fixed code: what a
  dashboard groups by), `http_status`, `endpoint` (host and path, IDs replaced
  by `:id`) and `error_message` (cleaned, 200 characters max).
- **Privacy.** No IP addresses, Wi-Fi names, coordinates, school names, Windows
  user names or install paths on events. Free-text messages go through
  `sanitizeMessage()`. Autocapture and session replay are off.
- **Schools.** Events carry the school's giga ID (the unique ID made for each
  school) as the `school` group key. The group also holds the school's
  `external_id` (the school ID from the school records, which schools type to
  register) and `name`, from the school record the registration saved, so
  dashboard tables can show giga ID, external ID and name side by side.
- **Volume.** Pings (every 15 minutes) are summarised once a day in
  `device_heartbeat` instead of one event each. The backend only reports
  problems, never every accepted measurement.

## Events by flow

### 1. Install, register, first test

| Event | Sent when | Key properties |
|---|---|---|
| `app_first_launch` (main) | First launch on this PC (userData state file) | `version`, `install_scope` (`all_users` / `per_user` / `other`) |
| `app_launched` (main) / `app_started` | Every launch | `install_scope`, `manufacturer`, `model` |
| `onboarding_started` | Onboarding slides shown | `language` |
| `consent_accepted` | "Start Registration" after ticking the policies | |
| `country_detected` / `country_detection_failed` | IP-based country lookup | `detected_country` / failure fields |
| `country_check_failed` | Country not whitelisted (`error_code: not_available`) or the check failed | `country_code` |
| `country_confirmed` | Country confirmed | `country_code`, `detected_country`, `overridden` |
| `school_search_performed` / `school_search_failed` | School ID search | `found`, `result_count` (band), `reason` |
| `school_selected` | School picked from the results | `country_code` |
| `registration_completed` | A new app instance registered | `registration_source` (`manual` / `auto`), `country_code`, `is_reregistration`, `minutes_since_logout`, `has_geolocation`, `has_hardware_id`, `has_serials` (a motherboard or disk serial went with it). Manual: `duration_ms` (since onboarding), `country_mismatch`. Auto: `trigger` (`startup` / `late_hardware_id` / `after_remote_deactivation` / `retry` / `claim_refused`) |
| `registration_failed` | A registration failed. Auto: the app goes on with the PC's registration it found, and tries again at the next start | `registration_source`, `trigger` (auto), `reason` (manual) + failure fields (`context_unavailable` when the PC couldn't be read) |
| `app_instance_claimed` | An install from before app instances attached its new ID to its registration (2.0.4 migration) | |
| `app_instance_claim_failed` | That failed | `outcome` (`registering_on_its_own`: the registration is another install's or gone, so it registers by itself; `will_retry`) + failure fields |
| `registration_lost` | Saved school no longer registered on the backend | `reason` |
| `hardware_id_unavailable` / `hardware_id_resolved` (main) | No usable hardware ID; found on a retry | `where`, `retry`, `attempts` |

Funnel: `app_first_launch` → `onboarding_started` → `consent_accepted` →
`country_confirmed` → `school_search_performed (found)` → `school_selected` →
`registration_completed (manual)` → `measurement_completed (trigger = first)`.

A PC that already has a registration skips the funnel: the app registers a new
app instance at the same school by itself (`registration_completed`,
`registration_source = auto`).

### 2 and 3. Speed test and ping, manual and scheduled

| Event | Sent when | Key properties |
|---|---|---|
| `measurement_started` | A test starts | `trigger` (`first` / `manual` / `startup` / `daily`), `slot` (`morning` / `afternoon` / `evening` / `startup`) |
| `measurement_retrying` | Locate server failed, retrying | `attempt`, `phase`, `error_code` |
| `measurement_completed` | Test finished and saved | `duration_ms`, `ping_ms`, `prep_ms`, `test_ms`, `uploaded`, `server_country`, `metro_rank`, `locate_tier` (`priority` / `public`), `priority_locate_error`, `download_server_measurement`, `upload_server_measurement`, `wifi_status`, `ssid_source`, `device_identity_read`, `device_context_read` |
| `measurement_failed` | Test failed for good | `phase` (`ping` / `prep` / `net_info` / `locate` / `download` / `upload` / `finalize`), `error_code`, `ndt_error` + failure fields |
| `scheduled_test_rescheduled` | Scheduled test retried later | `reason` (`no_network` / `test_failed`), `retry_attempt`, `delay_ms` (offline: first retry only) |
| `scheduled_test_missed` | A window ended without a test | `reason` (`slot_ended_before_run` = PC off or asleep, `no_network`, `test_failed`), `retry_attempts` |
| `measurement_uploaded` | Delivered in realtime | `notes`, `scheduled_slot`, geolocation fields (below) |
| `measurement_queued_offline` | Upload failed, queued for sync | failure fields, geolocation fields |
| `measurement_rejected` | Backend refused it (not queued: it is already in `measurements_failed`) | `source` (`realtime` / `sync`), `reason`, `count` |
| `measurements_synced` / `measurements_sync_failed` | Offline queue sent / failed | `batch_size` + failure fields |
| `device_heartbeat` | Once per local day, per app instance | `registered`, `has_app_instance_id`, `registration_pending` (going on with the PC's registration until its own is stored), `app_instance_claim_pending`, `scheduled_testing`, `upload_enabled`, `online`, `hours_since_last_measurement`, `pending_measurements`, `ping_attempts_24h`, `ping_successes_24h`, `ping_unsynced`, `top_ping_error` |

`error_code` for tests: `locate_failed`, `no_result`, `websocket_error`,
`timeout`, `network`, `unknown`.

### 4. App update

All sent by the Electron main process through the telemetry bridge. Staging
and dev builds have the updater off; testing this flow needs a build with
`mode: 'prod'` pointed at a test update feed.

| Event | Sent when | Key properties |
|---|---|---|
| `update_available` | electron-updater found a release | `from_version`, `to_version` |
| `update_downloaded` | Download finished, prompt shown | `from_version`, `to_version` |
| `update_prompt_answered` | Restart / Later | `action` |
| `update_failed` | Any updater error | `phase` (`check` / `download` / `install`), `error_code` (`network` / `signature` / `disk_full` / `permission` / `feed_not_found` / `unknown`) |
| `app_updated` | First launch on a new version (the update really installed) | `from_version` (null when upgrading from a build before this plan), `to_version` |
| `app_quit` | App quits | |
| `main_process_error` | Uncaught main-process error (10 per run max) | `error_type`, `error_message` |

### 5. Logout and register again

| Event | Sent when | Key properties |
|---|---|---|
| `logout_started` / `logout_cancelled` | Logout dialog opened / closed without logging out | |
| `logout_failed` | Wrong school ID typed (`error_code: wrong_school_id`) or unexpected error | failure fields |
| `logout_completed` | Logged out (sent at once: the page reloads) | `backend_deactivated`, `deactivate_error_code`, `deactivate_http_status` |
| `device_deactivated_remotely` | Another app instance on this PC logged out: the backend deactivates every app instance of the PC at that school | |
| `device_status_check_failed` | Startup registration checks failed (the app continues) | `check`, failure fields |

Funnel: `logout_completed` → `registration_completed (is_reregistration = true)`
within 24 hours.

### 6. Background capture (no person involved)

Geolocation runs with each upload, so its outcome rides on `measurement_uploaded`,
`measurement_queued_offline` and `measurement_rejected`:

| Property | Values |
|---|---|
| `geo_status` | `resolved`, `cache_reused`, `no_access_points`, `resolve_failed`, `failed` |
| `geo_sent` | whether a location went with the measurement |
| `geo_ms`, `geo_error_code`, `network_changed`, `access_points` (band), `wifi_scan_failed` | |

Wi-Fi and device reads ride on `measurement_completed`: `wifi_status`
(`ok`, `location_disabled`, `no_adapter`, `wlan_service_off`, `unknown`,
`unavailable`), `ssid_source`, `device_identity_read`, `device_context_read`,
`prep_ms`.

### Backend events (giga-meter-backend, `src/analytics`)

What only the server knows. Same person (the device ID), app instance and
groups as the app; an event whose registration has no device ID stays on the
school, without a person. Off unless `POSTHOG_API_KEY` is set.

| Event | Sent when | Key properties |
|---|---|---|
| `server_device_registered` | Every registration (auto or manual): one app instance on a device | `app_instance_id`, `registration_source`, `registration_user_id`, `repeat`, `has_device_id`, `device_id_flags`, `app_instances_for_device`, `active_app_instances_for_device`, `anomaly` (5+ app instances on one device ID) |
| `server_measurement_rejected` | Measurement stored in `measurements_failed` | `reason` (`school_doesnt_exist` / `wrong_country_code`), `upload_protocol`, `offline_synced` |
| `server_measurement_flagged` | Location too far from the school or too vague | `distance_band`, `accuracy_band` |
| `server_device_deactivated` | Logout reached the backend | `deactivated`, `app_instances_deactivated` (more than 1: other Windows users' app instances on the PC were logged out too) |
| `server_registration_request_created` | Missing school requested from the app | `verification_status`, `dispatch_failed` |
| `server_registration_rejected` | That request rejected | `country_iso3` |

## Dashboards

All dashboards are named "Giga Meter · …" and filtered to production with a
dashboard filter, `app_mode = prod` (switch it to `stg` to look at staging).
The filter drives every tile: the SQL tables take it through `{filters}`.

0. **Release adoption** (the key release metric): how fast schools, devices
   and app instances move to the latest version, for every day of the last 90.
   - **Schools with at least one device on the latest version**, and the
     schools known, per day; the same for devices and app instances.
   - Each device counts at the version of its **latest report** (its last
     event, however old; up to 15 months back), with the school it reported
     from. A school is on the latest version when any of its devices' latest
     report is. App instances count at their own latest report.
   - For each day, *latest version* is the highest version among the devices'
     latest reports that day.
   - "Known" counts every device and school PostHog has heard from, so ones
     that stopped using the app stay in them.
   - Latest version by country today, and the schools not on it yet (giga ID,
     external ID, name, country, devices, highest version, last report).
   - Schools and devices per version, updates installed per day, restart
     prompt answers, update failures: why an upgrade is slow.
   - PostHog only hears from 2.0.4 and later, so schools still on older
     versions are not in the "known" counts. The counts of schools on the
     latest version are complete; a share of all schools needs the database.
1. **Release health** (the "is everything working" page): active devices
   (24 h, 7 d: persons with a `device_heartbeat` or a measurement) and active
   app instances, test success rate
   (`measurement_completed` / `measurement_started`) by `trigger`, upload
   success rate (`measurement_uploaded` / all upload outcomes), offline backlog
   (`pending_measurements`), registration conversion, exceptions per device,
   version adoption (`app_version` on `device_heartbeat`). Each with an alert.
2. **Onboarding funnel**: the funnel above, by country, with failure reasons
   per step and `duration_ms`.
3. **Measurements**: started / completed / failed by `trigger` and `slot`;
   failures by `phase` × `error_code`; `scheduled_test_missed` by `reason`;
   `prep_ms` and `duration_ms` p50 / p95; per `app_version`.
4. **Ping and uptime**: `ping_successes_24h / ping_attempts_24h`, devices with
   no successful ping, `top_ping_error`.
5. **Updates**: adoption over time, `update_available` → `update_downloaded` →
   `update_prompt_answered (restart)` → `app_updated`, `update_failed` by
   `phase` and `error_code`.
6. **Logout and re-registration**: logouts, `logout_failed` by code,
   `backend_deactivated = false`, re-registration within 24 h.
7. **Background capture**: `geo_status` mix, `wifi_status` mix (the Windows 11
   24H2 Location-permission problem shows as `location_disabled`), hardware ID
   resolution, `server_measurement_flagged` by band.
8. **Errors**: every event with an `error_code`, grouped by event and code, with
   affected devices and last seen; `$exception` by type and version; links to
   the device's timeline.
9. **Devices and app instances** (the base unit):
   - Devices live with at least one app instance (24 h, 7 d), by school and
     country; registered devices that went silent.
   - App instances per device (distinct `app_instance` groups per person),
     active app instances, registrations by `registration_source`, automatic
     registrations failing or pending (`registration_pending`).
   - The 2.0.4 migration: `app_instance_claimed` vs `app_instance_claim_failed`
     by `outcome`, installs with `app_instance_claim_pending`.
   - Registrations without a device ID (`has_device_id = false`) or without
     serials (`has_serials = false`), and `device_id_flags` (a hardware value
     that changed under the same device).
   - The **anomaly alert**: any `server_device_registered` with
     `anomaly = true`, i.e. 5 or more app instances mapping to one device ID
     (likely PCs sharing one hardware signature);
     `active_app_instances_for_device` tells cloned PCs (many active) from one
     PC's logins (one active).

## Environments

- **One PostHog project for production and staging** (the free plan has
  one). Every event says which it came from in `app_mode` (`prod` / `stg` /
  `dev`), and every dashboard filters on it.
- App builds: `_environment.prod.ts` sets `posthogKeyProd` and
  `posthogKeyStg` to the same project key; leave `posthogKeyDev` empty unless
  testing analytics. The Electron build warns when the key for its mode is
  missing (`electron/scripts/generate-build-mode.js`). An older
  `posthogApiKey` entry is not read by anything.
- Backend: `POSTHOG_API_KEY` is the same key, and `POSTHOG_APP_MODE` says
  `prod` or `stg` (worked out from `SENTRY_ENVIRONMENT` / `NODE_ENV` when
  unset; set it on production so its events don't drop out of the
  dashboards).
- A PC registered on both staging and production gets the same device ID in
  both (the ID is a hash of its hardware), so it is one PostHog person with
  events of both modes. Only test PCs do this; the `app_mode` filter keeps the
  dashboards apart.
- In PostHog: discard client IP data. Group types: `school`, `country` and
  `app_instance` (each created by the first event that carries it).

## Checking events against the database

| PostHog | Database (staging, via Superset) |
|---|---|
| persons (devices) | distinct `dailycheckapp_school.device_id` (and `measurements.device_id`) |
| `app_instance` groups | `dailycheckapp_school.app_instance_id` (null on rows from before 2.0.4 until claimed) |
| `server_device_registered` | `dailycheckapp_school` rows (app instances), `registration_source`, `device_id_flags` |
| `registration_completed` by `registration_source` | new `dailycheckapp_school` rows by `registration_source` |
| `app_instance_claimed` | rows from before 2.0.4 whose `app_instance_id` got filled in |
| `measurement_uploaded` + `measurements_synced` | `measurements` rows (by `app_instance_id`, `device_id`) |
| `server_measurement_rejected` | `measurements_failed` rows by `reason` |
| `server_measurement_flagged` | `measurements` with `detected_location_is_flagged` |
| `ping_attempts_24h` | `connectivity_ping_checks` (by `app_instance_id`); the daily summary by `device_id` |
| `server_registration_request_created` | `school_new_registration` |
